## 0. 一页速览

**一句话**：Gesto 是一个用普通笔记本摄像头控制课堂演示的桌面软件——右手一挥翻 PPT、
两手比框读懂屏幕上的字（离线 OCR + 大模型给出中文译文与讲解）、握拳关掉、张开手掌再叫回来、
左手握拳张开缩放页面。

**交互闭环**（7 个手势，按左右手分工，同一摄像头、互不冲突）：

| 手 | 手势 | 系统动作 | 实现手段 |
|---|---|---|---|
| 右手 | 五指张开 · 向左划 | 下一页（→） | 轨迹方向判定 + 模拟按键 |
| 右手 | 五指张开 · 向右划 | 上一页（←） | 同上 |
| 右手 | 食指+中指（其余收拢）· 横划 | 连翻模式（冷却 0.18s） | 姿态判定 + 缩短冷却 |
| 右手 | 握拳 | 面板开着→收面板；没面板→退出放映（Esc）；2.5s 内连握两次→回桌面 | 四指比值 + 连续帧确认 |
| 右手 | 张开手掌 · 停住 0.8s | 复原刚关掉的面板（6s 内有效） | 掌心逗留判定 + 面板快照 |
| 左手 | 握拳 | 缩小页面（Ctrl+-） | 左右手标签 + 按键注入 |
| 左手 | 张开手掌 · 停住 0.8s | 放大页面（Ctrl+=） | 同上 |
| 双手 | 食指伸 + 中指收 · 比框 | 截取框内屏幕区域 → OCR → 译文+讲解面板 | 屏幕坐标映射 + 离线 OCR + 大模型 |

> 左右手由 MediaPipe 的 `handedness` 输出判定。**该模型假设输入画面是镜像的**（自拍视角），
> 但摄像头驱动本身是否已经镜像过因机器而异：本机实测发现驱动已镜像，程序再 `cv2.flip` 一次
> 反而把前提抵消掉，导致右手被标成左手（见 5.13）。所以现在**默认交换左右手**，
> 并在设置里提供「左右手判定互换」开关；预览窗左上角常驻 `HAND: L/R` 供现场核对。

## 2. 系统架构

### 2.1 运行时数据流

```
                  ┌──────────────── 每帧循环（单线程，主循环）────────────────┐
 摄像头 ──▶ cv2.VideoCapture ──▶ cv2.flip(镜像) ──▶ HandLandmarker.detect_for_video

                    ▼                                   ▼                    ▼
            [双手] FrameTracker               [单手] SlideTracker      [单手] any_fist
            框的平滑/稳住判定                  轨迹门禁→next/prev        四指比值→握拳
                    │                                   │                    │
                    │ 稳住 1s                            │ 命中                │ 连续5帧
                    ▼                                   ▼                    ▼
        ImageGrab 截取屏幕区域               pyautogui.press(→/←)   Esc / Win+D / 收面板
                    │
                    ▼
        RapidOCR（离线）→ 术语库匹配 ──命中──┐
                    │                    ├──▶ 结果面板（Tk 透明浮层）
                    └──未命中/需详解──▶ 大模型 JSON（译文+讲解+关键词）
```

三个手势的**互斥关系**由"手的数量"天然分开：双手在场时翻页判定直接上锁
（`slide.lock()`），避免框选时手臂横移被误判为挥手。

### 2.2 关键设计选择及理由

1. **为什么浮层画在真实桌面上，而不是摄像头预览里**
   摄像头看到的是"人"，不是屏幕；手在画面里的位置与屏幕上要框哪里没有几何对应关系。
   把框实时画在**真实屏幕**上，人眼会自己纠正映射误差——这比任何标定都稳。
2. **为什么用比值判手指伸展，而不用关节角度**
   `|指尖-手腕| / |指根-手腕|` 与手离摄像头远近无关（尺度不变），一个除法就够，
   不需要求解 3D 姿态。实测真握拳 0.63~0.83、张开手 1.16~1.90，两段区间不重叠。
3. **为什么翻页不用"速度阈值"而用时序门禁**
   挥手之后手一定会回位，而"回位"与"故意反着挥"在几何上是**同一个动作**（见 5.4），
   只能靠时序区分。
4. **为什么引擎单独跑一个进程**
   引擎会独占摄像头、会开 OpenCV 窗口、可能崩；UI 不该跟着崩。同时便于把
   "手势算法"与"桌面外壳"解耦——两者可以分别演进。

## 3. 核心算法与关键代码

### 3.1 手指伸展判定（尺度不变）

```python
# hand-ocr/hand_frame_ocr.py
def hand_ratios(hand):
    """返回 (四指比值, 手掌尺寸)。比值 = |指尖-手腕| / |指根-手腕|，与手的远近无关。"""
    wrist = hand[0]
    rs = []
    for tip, pip in ((8, 6), (12, 10), (16, 14), (20, 18)):
        rs.append(_dist(hand[tip], wrist) / max(1e-6, _dist(hand[pip], wrist)))
    return rs, _dist(hand[0], hand[9])      # 第二项是手掌尺寸，用来滤掉噪点帧
```

配套阈值：

```python
INDEX_RATIO = 1.10       # 食指伸出判定：指尖-手腕 / 食指根-手腕 距离比
FIST_MAX_RATIO = 0.95    # 四指比值全部小于此值才算握拳（实测真握拳 0.63~0.83）
FIST_CONFIRM = 5         # 握拳需连续几帧确认（防止抖动误关）
MIN_PALM = 0.03          # 手掌尺寸小于此值视为噪点，本帧丢弃
```

`1.10` 与 `0.95` 之间留了 0.15 的中间带，避免"半握"在两者之间反复跳变。

### 3.2 单手滑动翻页：三道门禁

这是整个项目里调得最久的部分。最终实现（`SlideTracker.update`，节选真实代码）：

```python
        # ---------- 4) 回撤复位跟踪：手是否已从上次动作的终点往回撤过 ----------
        if self.retract_peak is not None and not self.retract_ok:
            if (cx - self.retract_peak) * self.ext_sign > 0:
                self.retract_peak = cx                      # 还在往同方向推进，更新最远点
            elif (self.retract_peak - cx) * self.ext_sign >= RESET_DIST:
                self.retract_ok = True                      # 回撤到位，可以再同向翻一页

        if not self.armed or len(self.buf) < 4:
            return ""
        if (now - self.last_action) < SWIPE_COOLDOWN:
            return ""

        xs = [b[1] for b in self.buf]
        ys = [b[2] for b in self.buf]
        span_x = max(xs) - min(xs)
        span_y = max(ys) - min(ys)
        if span_x < SWIPE_DIST:                        # 位移不够
            return ""
        if span_y > span_x * SWIPE_MAX_TILT:           # 以竖直为主，不算横挥
            return ""

        # 方向不看"首尾差"，看两个极值谁先出现
        go_right = xs.index(max(xs)) > xs.index(min(xs))
        dx_net = xs[-1] - xs[0]
        if abs(dx_net) < max(SWIPE_DIST * 0.5, span_x * 0.5) or (dx_net > 0) != go_right:
            return ""                                  # "划过去又原路划回"的抖动

        act = ("prev" if go_right else "next") if SWIPE_LEFT_IS_NEXT \
            else ("next" if go_right else "prev")

        # ---------- 5) 反向锁定：吞掉手回位那一下 ----------
        if self.block_dir and act == self.block_dir:
            if self.retract_peak is not None and \
                    (self.retract_peak - cx) * self.ext_sign >= RESET_DIST:
                self.retract_ok = True
            self.buf.clear()
            return ""

        # ---------- 6) 同方向但还没回撤：一次长挥不连发 ----------
        if act == self.dir and not self.retract_ok:
            self.buf.clear()
            return ""

        self.last_action = now
        self.dir = act
        self.block_dir = "prev" if act == "next" else "next"   # 反向先锁住
        self.block_until = now + RETURN_TTL
        self.ext_sign = 1 if go_right else -1
        self.retract_peak = cx
        self.retract_ok = False
        return self.dir
```

对应参数（含实测依据）：

```python
SWIPE_WINDOW = 0.50      # 滑动判定时间窗口（秒）
SWIPE_DIST = 0.09        # 窗口内横向最小位移（占画面比例）
SWIPE_COOLDOWN = 0.30    # 两次翻页之间的冷却（五指模式）
SWIPE_COOLDOWN_FAST = 0.18   # 食指+中指连翻模式的冷却
SWIPE_MIN_FINGERS = 3    # 五指模式下至少 3 指伸出才算"在滑动"
TWO_FINGER_INDEX = 1.10  # 连翻模式：食指/中指伸出阈值
TWO_FINGER_FOLD = 1.05   # 连翻模式：无名指/小指平均比值低于此值算收拢
SWIPE_MAX_TILT = 1.6     # 允许斜挥：竖直跨度 <= 横向跨度 × 1.6
RESET_DIST = 0.10        # 同方向连发前必须回撤的距离（两种模式都强制）
FLIP_PAUSE = 0.20        # 折返点停多久才算"故意反着挥"（低于此值视为手在回位，吞掉）
RETURN_TTL = 2.0         # 反向锁定的保险丝
STILL_RADIUS = 0.03      # 停稳判据：掌心不离开这个半径的小圈
```

**三道门禁的分工**（缺一不可）：

| 门 | 解决什么 | 判据 |
|---|---|---|
| 位移/方向 | 是不是一次真实的横挥 | 横向跨度 ≥0.09、非竖直为主、净位移与方向一致 |
| 回撤复位 | 一次长挥不要连发好几页 | 同向再触发前，手须先退回 `RESET_DIST`（两种模式都不放松） |
| 反向锁定 | 手回位不要被当成反方向翻页 | 翻页后反向动作先吞掉，直到折返点停够 `FLIP_PAUSE`(0.20s) 才放行 |

> `FLIP_PAUSE` 是 2026-10-25 的重要修订：原来要求停稳 0.65 秒，导致「左滑完马上右滑」
> 第二下被吞（用户报"两次操作被识别成一次"）。逐帧数据显示，挥手后手的自然回位只在折返点
> 停 **0.07~0.10 秒**，而人"故意反着挥"会停 **0.2 秒以上** —— 0.20 正好卡在两者之间，
> 既接住了快速反向，又继续吞掉自然回位。真实录屏重放验证：4 次挥动仍为 4 次触发，无虚增。


**"稳住"的判定用的是"逗留"，不是"速度低"**（踩过的坑见 5.3）：

```python
    def _dwell(self, now, cx, cy, span):
        """掌心在最近 span 秒内是否始终待在半径 STILL_RADIUS 的小圈里。"""
        if not self.hist:
            return False
        if now - self.hist[0][0] < span - 0.02:   # 时间跨度还不够
            return False
        for t, x, y in self.hist:
            if now - t <= span + 1e-6 and \
                    (x - cx) ** 2 + (y - cy) ** 2 > STILL_RADIUS ** 2:
                return False
        return True
```

### 3.3 双手取景框

```python
def detect_frame_box(hands):
    """两只手都伸出食指时，用两手拇指尖+食指尖围出的矩形作为取景框。"""
    if not hands or len(hands) < 2:
        return None
    ok = []
    for h in hands:
        rs, palm = hand_ratios(h)
        if palm < MIN_PALM:
            continue
        if rs[0] > INDEX_RATIO:          # 食指伸出（rs[0] 对应 8/6）
            ok.append(h)
    if len(ok) < 2:
        return None

    h_a, h_b = sorted(ok[:2], key=lambda h: (h[0].x + h[9].x) / 2.0)
    pts = [h_a[4], h_a[8], h_b[4], h_b[8]]      # 4=拇指尖 8=食指尖
    x0 = min(p.x for p in pts); x1 = max(p.x for p in pts)
    y0 = min(p.y for p in pts); y1 = max(p.y for p in pts)
    if (x1 - x0) < MIN_BOX_W or (y1 - y0) < MIN_BOX_H:
        return None
    return (max(0.0, x0), max(0.0, y0), min(1.0, x1), min(1.0, y1))
```

用**拇指尖+食指尖四个点**而不是手腕或掌心：四个指尖正好是"取景框"的四个角，
人的直觉就是拿手指比出矩形的角，不需要额外校准。

### 3.4 摄像头坐标 → 屏幕坐标（含放大）

摄像头整幅画面本来就 1:1 映射到整屏，但**两只手根本张不到摄像头的四个边**，
所以不加处理时框只能覆盖屏幕中间一块。下面这张表是按"手的活动范围占画面
60%（宽）×50%（高）"算出来的——这个比例是按两种手在笔记本摄像头前的可达范围**估算**的，
没有做用户实测，所以表里的百分比应当作"量级参考"而不是精确标定值。
解决办法是绕画面中心放大：

```python
def _zoom_norm(v):
    """摄像头坐标绕中心放大后夹回 [0,1]：放大后手不必张满画面，框也能贴到屏幕边缘。"""
    return min(1.0, max(0.0, 0.5 + (v - 0.5) * FRAME_ZOOM))


def box_to_screen(box, sw, sh):
    x0, y0, x1, y1 = box
    fx = lambda v: (v - SRC_L) / max(1e-6, SRC_R - SRC_L)
    fy = lambda v: (v - SRC_T) / max(1e-6, SRC_B - SRC_T)
    X0, X1 = fx(_zoom_norm(x0)), fx(_zoom_norm(x1))
    Y0, Y1 = fy(_zoom_norm(y0)), fy(_zoom_norm(y1))
    return (int(round(X0 * sw)), int(round(Y0 * sh)),
            int(round(X1 * sw)), int(round(Y1 * sh)))
```

实测覆盖效果（假设手的活动范围占画面 60%，1920×1080 屏）：

| `FRAME_ZOOM` | 框能覆盖屏幕 | 备注 |
|---|---|---|
| 1.0 | 60% × 50% | 不加放大的原始行为 |
| 1.5（默认） | 90% × 75% | 折中值 |
| 1.8 | 100% × 90% | |
| 2.2 | 100% × 100% | 能全屏，但更难停准 |

放大只影响"摄像头→屏幕"这一步，**不影响"稳住 1 秒"的判定**（阈值都在摄像头坐标系里），
代价是同一段手势对应的屏幕位移被放大，框更难停稳。

### 3.5 握拳的多义分派

同一个"握拳"在两个场景里都被当成本能动作，所以按上下文分派（真实主循环代码）：

```python
def looks_english(s):
    """判据：至少有一个 2 个字母以上的英文单词，且字母数明显多于汉字数。
    故意不算单个大写字母 —— 否则 P(A|B)=P(B|A)P(A)/P(B) 这种纯公式会被当成英文。"""
    words = re.findall(r"[A-Za-z]{2,}", s)
    letters = sum(1 for ch in s if ch.isascii() and ch.isalpha())
    cjk = sum(1 for ch in s if "\u4e00" <= ch <= "\u9fff")
    return bool(words) and letters > cjk * 2
```

### 4.2 进程模型：引擎是子进程，日志走文件

引擎单独进程跑，UI 只负责启停与展示。**这里有个必须绕过的坑**：GUI 方式打包后，

### 4.3 高 DPI：不声明就必然发虚

第一版在 2560×1600 / 150% 的机器上字很糊，原因不是字号，而是**进程没声明 DPI 感知**，
Windows 把 1180×762 的窗口整体按 1.5 倍位图拉伸。解决：

```python
def enable_dpi_awareness():
    if os.name != "nt":
        return
    try:
        ctypes.windll.shcore.SetProcessDpiAwareness(1)     # 系统级 DPI 感知
    except Exception:
        try:
            ctypes.windll.user32.SetProcessDPIAware()
        except Exception:
            pass


def px(v):
    """96dpi 设计稿上的像素 → 当前屏物理像素。"""
    return int(round(v * SCALE))


def make_root():
    """DPI 感知必须在 Tk() 之前开，SCALE 必须在任何 px() 之前算出来。"""
    global SCALE
    enable_dpi_awareness()
    root = tk.Tk()
    SCALE = max(1.0, min(2.5, root.winfo_fpixels("1i") / 96.0))
    return root
```

所有布局尺寸（内边距、图标、圆角、滑块长度、滚动条、窗口尺寸）都过一遍 `px()`，
**字体点数不动**——Tk 的 `tk scaling` 会随 DPI 自动从 1.33 变 2.0（9pt 行高 17px→24px），
字体自己跟着放大。结果：窗口变成 1768×1142 物理像素原生渲染，文字由位图拉伸变为矢量绘制。

## 5. 工程问题清单（现象 → 根因 → 证据 → 修法）

这一节是整份材料里最"实"的部分：每条都对应一次真实的失败与复现。

### 5.1 `.bat` 中文变乱码 / 命令被吞

- **现象**：双击启动脚本报 `'自动识别框内文字并弹出释?echo' 不是内部或外部命令`。
- **根因**：bat 文件存成 UTF-8，而 cmd 按 GBK 解析，中文字节错位把换行吞了。
- **证据**：文件里 264 个非 ASCII 字节；改为纯 ASCII 后 0 个。
- **修法**：所有启动脚本改成纯 ASCII（英文注释）。

### 5.2 张开手被误判成握拳 → 误退放映

- **现象**：用户张开五指，放映被退出。
- **根因**：判定写成"伸指数 ≤1 即握拳"。实测帧 238/519 的四指比值为
  `[1.35, 1.01, 0.99, 1.0]`，只有 1 个超过 1.10 → 被当成"1 指伸展"，落进握拳分支。
- **修法**：改成"四个比值**全部** < 0.95 才算握拳"，加连续 5 帧确认和手掌尺寸下限。
  实测真握拳 0.63~0.83，与张开手 1.16~1.90 完全不重叠。

### 5.3 判"停稳"不能用速度低

- **现象**：设了"动作后必须停稳 0.16 秒"，用户快速连挥时第二下被静默丢弃。
- **根因**：手在折返点会先减速再反向，那 0.2 秒减速看起来就像"停稳"；
  反过来，真的快速连挥时逗留时间不够又被判"没停稳"。
- **修法**：改为**逗留**判定——掌心在 N 秒内始终不离开半径 0.03 的小圈（`_dwell`）。
  并且容差必须小于一帧（`span-0.02`），否则窗口最老的样本会被跳过，实际停留比设定短。
- **最终形态**：解锁改用"轨迹攒够 4 帧即解锁"，不再依赖停稳；停稳只用于解除反向锁定。

### 5.4 连挥两次被读成"左、右、左"

- **现象**：连续两次左滑，PPT 出现 左→右→左 三次翻页。
- **根因**：挥手后手会**回位**，回位与"故意反着挥"在几何上完全相同。
  逐帧实测：16.53→16.87s 掌心 x 从 0.238 到 0.454（真实挥动），
  16.90~16.97s 只停了 **0.07~0.10 秒**，17.00→17.20s 又走回 0.452→0.322，
  这段回位位移 **0.13 > 阈值 0.10**，于是被判成一次反向翻页。
- **修法**：两道时序闸（回撤复位 + 反向锁定）。开关对照实验：
  关闭反向锁定 → 触发 `[(16.66,'next'), (17.23,'prev')]`；开启 → 只有 `[(16.66,'next')]`。
- **代价**（已告知用户）：想翻回上一页必须在折返点停一下再反着挥。这是几何不可区分下的必然取舍——
  宁可少一次，不要多一次。
- **后续修订（10-25）**：这个"停一下"最初定成 0.65 秒，太长，导致快速反向操作被吞（见 5.11），
  现已按逐帧数据下调到 0.20 秒。

### 5.5 一次挥手翻两页

- **现象**：录屏里 14.08s 与 14.44s 连发两次翻页。
- **根因**：挥手收尾时手心会在终点抖约 0.05，而旧的 `RESET_DIST=0.05` 刚好被这次抖动满足，
  于是"抖一下再推"被判成第二次挥手。
- **证据**：逐帧数据里 14.24s 峰值 -1.011，14.44s 回到 -0.959，位移 0.052 ≥ 0.05。
- **修法**：`RESET_DIST` 提到 0.10（不小于 `SWIPE_DIST`）；并且反向吞掉那一支**不再无条件**
  置 `retract_ok=True`，只有真的退回 `RESET_DIST` 才算复位完成。

### 5.6 左滑在第一页上完全没反应

- **现象**：用户报"左滑不响应"，右滑正常。
- **证据（这是本项目最关键的一次排查）**：把用户的手机录屏逐帧过 HandLandmarker，
  导出手心坐标成 CSV，再离线重放 `SlideTracker`（不依赖摄像头）。
  录屏里 4 次真实左挥（10.7 / 12.6 / 13.9 / 15.4s，横向位移 0.21~0.60），
  旧代码判定结果**全部是 `prev`**（按 ← 上一页）——而用户当时停在第 1 页，上一页当然毫无反应。
- **根因**：方向映射写反。摄像头正对人时，本人右侧落在图像左侧；`cv2.flip(1)` 后
  `x' = 1 - x`，本人右侧变成 x' 大。用户口径是"右滑=上一页、左滑=下一页"，
  所以 `go_right` 应映射到 `prev`，而代码写成了 `act = "next" if dx > 0`。
- **修法**：改正映射并加 `SWIPE_LEFT_IS_NEXT` 开关（可用环境变量 `HAND_OCR_SWIPE_FLIP=1` 反向），
  同时把方向判定从"首尾差"改成"两个极值谁先出现"（回位会抵消首尾差，但极值先后稳定）。
- **验证**：同一段录屏重放，4 次真实左挥 → 4 次 `next`，严格 1:1，无虚增无漏判。

### 5.7 手势调参不能只靠感觉

- **做法**：把手势判定逻辑与摄像头解耦，抽出 `hand-ocr/tests/`：
  - `data/track_raw.csv`：录屏逐帧导出的手心坐标/伸指数/手掌尺寸（701 帧）
  - `replay_track.py`：离线重放判定器，对比新旧方向映射
  - `regress_swipe.py`：13 条合成轨迹回归（连挥三次、停 0.8s 反挥、回位必须吞掉、
    竖直抬手不算、45° 斜挥算……）
  - `panel_layout.py`：用隐藏 Tk 画布真跑面板渲染，量包围盒查溢出
- **结果**：13/13 通过；改任何阈值前先跑这两条命令，避免"改好了 A 坏了 B"。

### 5.8 界面文字"叠在一起"（实际是纵向被压扁）

- **现象**：卡片行副标题看起来像两层字重叠。
- **根因**：行高写死 62px，内部可用高度只有 38px，而"11pt 标题（20px）+ 间隔 + 9pt 副标题（23px）"
  需要 45px，副标题被 Tk 压成 **9px** 高。
- **修法**：改成按内容算高度——`update_idletasks()` 后取 `winfo_reqheight()`。
- **顺带**：给布局自检加了**纵向裁切检查**（`Label.winfo_reqheight() > winfo_height()`），
  只查溢出是发现不了这种问题的。

### 5.9 打包后引擎"活着但没日志"

- **现象**：`Gesto.exe --engine` 进程存活，但日志 0 行。
- **根因**：`console=False` 打包后子进程 `sys.stdout` 是 `None`，`print` 全部写进空对象。
- **修法**：见 4.2，改为"引擎写文件、UI tail 文件"。
- **排查手段**：`OpenInputDesktop` 判断桌面是否锁定；锁屏时 `ImageGrab` 只能抓到锁屏壁纸，
  抓窗口要改用 `PrintWindow`。

### 5.10 其他小坑（同样有据可查）

| 现象 | 根因 | 修法 |
|---|---|---|
| 桌面出现黑色矩形 | 圆角多边形把 `x0` 误写成 `y0`（5 个点） | 改正顶点列表 |
| Tcl 报 `application has been destroyed` | 临时 Tk 窗口销毁后又建第二个 Tk | 让浮层自己向 Tk 询问尺寸 |

### 5.11 用户报"左滑完马上右滑，两次被识别成一次"（10-25）

- **现象**：一次左滑后再快速右滑，只翻了一页（反向那一下没生效）。
- **根因**：5.4 引入的"反向锁定"要求手在折返点停够 **0.65 秒**才解除；人手做不到，
  于是所有快速反向操作都被当成"手在回位"吞掉。
- **数据依据**：同一段录屏逐帧统计——挥手后自然回位在折返点只停 **0.07~0.10 秒**，
  而"故意反着挥"时人会在折返点停 **0.2 秒以上**。两者之间有清晰的分界，不需要 0.65 这么长的门槛。
- **修法**：`FLIP_PAUSE` 0.65 → **0.20**；冷却 `SWIPE_COOLDOWN` 0.35 → 0.30。
- **回归**：新增 `hand-ocr/tests/regress_fast.py` 7 条用例，其中"左挥·停0.28s·右挥"
  期望 `['next','prev']`、且"左挥·回位只停0.10s·右挥"期望仍只有 `['next']` —— **7/7 通过**；
  老 13 条用例 **13/13 通过**；真实录屏重放仍是 4 挥 → 4 次，无虚增。

### 5.12 关掉面板后握拳，页面自己"弹回来"（10-25）

- **现象**：用户以为程序有个"张开手复原"的手势，因为握拳关掉面板后，界面会自己回到原状。
- **根因**：**当时并没有复原手势**。真实路径是——面板关掉后再握一次拳时 `state["panel"]` 已是 None，
  代码进入"没面板就退出放映"的分支，第二次抓取还会发 `Win+D`；而 **Win+D 是开关**，
  桌面已经显示时再按一次会把窗口恢复回来，看起来就像"关掉的页面又回来了"。
- **修法**：①新增 `FIST_LOCK_AFTER_CLOSE=1.2`，关面板后 1.2 秒内不再响应 Esc/Win+D；
  ②按用户要求补上真正的复原手势（右手张开静止 0.8 秒，见 3.6），并把左右手拆开分工。

### 5.13 右手翻页被当成"左手放大"（10-25 实测，左右手判反）

- **现象**：用户右手做翻页动作，日志里连续三行 `[ZOOM] 左手张开静止 -> 放大页面`，
  同时预览窗显示 `HAND: L`——翻页完全没生效，页面反而被放大。
- **根因**：MediaPipe 的 handedness 假设"输入画面是镜像的"。程序为了预览窗像镜子，
  在检测前做了 `cv2.flip`，本是去满足这个前提；但**这台机器的摄像头驱动自己已经镜像过**，
  再 flip 一次就把镜像抵消掉，模型于是按"非镜像"解读，Left/Right 完全颠倒。
- **证据**：预览窗 `HAND: L` 与用户实际抬起的右手不符；日志里的 `[ZOOM]` 来自左手分支。
- **修法**：①`SIDE_SWAP` 默认改为 `True`（交换），并保留 `HAND_SIDE_SWAP=0` 与桌面端
  设置项「左右手判定互换」；②左手缩放增加 `n_hand == 1` 前置条件，双手场景不再误触发；
  ③预览窗底部调试行增加 `swap=0/1`，抬头就能核对。
- **教训**：这类"依赖外部库隐含假设"的代码，必须留一个**可现场观测的指示器**
  （这里是 `HAND: L/R`）和一个**不用改代码就能翻转的开关**，否则只能在别人的机器上才发现。

## 7. 局限与未验证项（申报材料里建议如实写明）

1. **未做标准数据集评测**。OCR 只在自造的 4 类截图（中英文、含公式）上验证过正确性，
   没有 CER/准确率这类可对外比较的指标。
2. **端到端帧率未系统测量**。已知关键点推理 19.6 ms/帧，但界面刷新、浮层重绘、
   日志追加都会占时间，实际摄像头预览帧率没有用工具测过。
3. **OCR 是主要延迟**（1.3–1.5 s/次），解法是放线程 + 面板先显示"识别中"，
   但用户仍会感到约 1.5 秒等待。
4. **大模型只验证了 2 次调用**（DeepSeek）。换厂商（千问等）对 JSON 的遵守程度未测，
   代码做了容错降级，但降级后的效果没有实测样本。
5. **手部遮挡/强逆光/深色皮肤等边界条件未测**。目前只在正常室内光线下自测通过。
6. **多显示器未测**。取景框映射用的是主屏尺寸。
7. **"稳住 1 秒"的 1.0 s 是经验值**，没有做用户实验来证明这是最舒服的时长。
   `RESTORE_DWELL=0.8s` 同理，是按"人抬手后自然停顿多久"估的，未做用户测试。
8. **左右手判定依赖摄像头驱动行为**。实测本机驱动已镜像，所以默认开了"互换"；
   换一台机器可能又要反过来。目前靠预览窗 `HAND: L/R` + 设置开关人工核对，
   没有做"自动检测哪只手在做翻页"这类自适应。
9. **左手缩放在 PPT 放映里没有效果**。发的是 `Ctrl+-` / `Ctrl+=`，浏览器、Word 里有意义，
   放映模式下这两个组合键没有缩放语义——报告里不应把它写成"通用缩放"。
10. **取景框现在要求中指收拢**。更早的版本只要"食指伸出"就给框，双手张开时也能触发；
    为了和左手放大手势区分才收紧，代价是比框动作更"标准"了一些，用户需要重新适应。
11. 应用商店发布**未完成**：本机没有 Windows SDK（缺 makeappx），MSIX 清单与打包脚本已就绪，
    但开发者账号与认证流程需要本人操作。
12. **安装包没有代码签名**，首次运行会被 SmartScreen 拦一次（点"更多信息 → 仍要运行"）；
    这是分发渠道问题，不是功能缺陷。

## 附：可直接写进申报书的"创新点"表述

以下是从实现里能**站得住**的差异点（每一条都能在代码里指出对应位置）：

1. **三个维度区分动作，而不是堆阈值**：手的数量（单手/双手）、手的身份（左/右）、
   手部的运动（横移/静止/收指）。7 个动作只靠这三个正交维度就分开了，
   没有一个是靠"再调一个阈值"硬凑出来的（`hand_frame_ocr.py` 主循环）。
2. **把"手回位"当成时序问题解**。几何上回位与反向挥完全相同，最终用"回撤复位 + 反向锁定"
   两道时序闸解决；反向门槛不是拍的，是从逐帧数据里量出来的（回位停 0.07~0.10s、
   故意反挥停 >0.2s，取 0.20s 分界），并有开关对照实验与 20 条可复跑用例支撑。
3. **"关掉能叫回来"只存快照，不重算**：握拳时把面板的内容与位置一起存下来，
   张开手掌静止 0.8 秒就原样画回去——不需要重新取景、不用再跑一次 3 秒的 OCR+大模型。
4. **框画在真实桌面上**，用人的眼睛替代标定：摄像头看到的是人不是屏幕，
   所以映射误差由人实时纠正，落地成本远低于屏幕-相机标定。
5. **离线优先的混合智能**：手部与文字识别全部本地（断网可用），
   大模型只负责"讲人话"，且约束成结构化输出（译文/讲解/关键词分离）。
6. **参数全部有实测出处**：每个阈值旁边的注释都写着它是怎么测出来的，
   配套 5 个可复跑脚本（合成回归 / 新规则回归 / 复原判定 / 录屏重放 / 面板排版）。
